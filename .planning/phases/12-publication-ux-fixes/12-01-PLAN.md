# Phase 12 Plan 01: Publication Feedback and State Reset

## Objective

Make a successful Save visibly trustworthy and return the active editor to a genuinely clean state without changing backend publication behavior.

## Requirements

- PUB-01, PUB-02, PUB-03
- RESET-01, RESET-02, RESET-03

## Tasks

### 1. Add popup state for Save outcomes

Update `ManageComponent` and its template to expose an accessible success dialog/toast for completed Save transactions. Derive the message from the authoritative Save/YouTube commit result so the popup distinguishes:

- published immediately/public on YouTube;
- saved with a future publication date/time and therefore scheduled;
- ordinary update/save without a YouTube publication job.

Keep the existing inline status for contextual recovery and ensure error paths never open the success popup. Add a dismiss action and prevent stale callbacks from reopening it after a reset.

### 2. Make resetEditor clear all upload and trailer lifecycle state

Centralize a per-editor reset of upload progress, busy/deleting/drag state, retryable files, trailer-video state, draft reservation subscriptions, YouTube job state/polling, and generation guards. Ensure the reset runs only after the complete Save/commit path succeeds and does not cancel or overwrite the successful server-side publication result.

Use a success-safe trailer-video transition before teardown so the old staged/uploading message cannot be replaced by the generic canceled message. Preserve explicit cancellation behavior for user-initiated reset/cancel actions.

### 3. Add focused component tests

Extend `manage.component.spec.ts` for immediate publication, scheduled publication, failed Save, reset progress/state, and stale callback protection. Assert that the popup message is derived from the returned publication state and that all File Management progress values return to zero after success.

- `npm run build` passes after implementation.
